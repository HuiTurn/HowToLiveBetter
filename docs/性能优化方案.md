# 人生指南库小程序 · 性能优化方案

> 检查范围：`miniprogram/` 全量源码（27 个 JS、22 个 WXML、65 张图片、34 篇文章 / 650 条正文）
> 检查时间：2026-10-03

---

## 一、体检结论（先看这个）

| 指标 | 当前实测 | 红线 | 判定 |
|---|---|---|---|
| 主包体积（源码） | **0.90 MB** | 2 MB | ✅ 安全 |
| 主包体积（含 `vibe_images/`） | **1.74 MB** | 2 MB | ⚠️ **只剩 260 KB 余量** |
| 分包 `pagesA` | **1.40 MB**（`steps.js` 占 1.37 MB） | 2 MB | ⚠️ 余量 600 KB，上游每轮同步 +20 KB |
| 总包 | 3.14 MB | 20 MB | ✅ 安全 |
| 单篇最大正文 | 44 条 / 40.8 KB（`b08`） | setData < 256 KB | ✅ 安全 |
| 详情页单页节点数 | 约 600 个（44 条 × 14 节点） | — | ⚠️ 首屏一次性渲染 |
| `usingComponents` | app.json 全局注册 5 个 | — | ⚠️ 冗余注入 |

**一句话诊断**：包体积没有爆，但 `vibe_images/`（876 KB 的本地截图）没被 `packOptions.ignore` 排除、正悄悄算进主包；运行时的主要开销集中在「1.37 MB 大对象一次性 require + 解析」和「系统信息同步 API 重复调用」两处。

📌 **我的假设**：优化目标是「启动更快 + 翻页不卡 + 包体积留足余量」，**不动任何现有功能和交互**。以下方案按此前提设计。

## 二、P0 立即做（零风险，纯减法）

### 1. 把 `vibe_images/` 排除出打包（主包 -876 KB，收益最大）

`project.config.json` 的 `packOptions.ignore` 里有 `docs`、`.autotmp`、`node_modules`，**但没有 `vibe_images`**。这 3 张本地截图（876 KB）会被打进主包，直接吃掉主包 49% 的额度。

```jsonc
// project.config.json
"packOptions": {
  "ignore": [
    { "value": ".eslintrc.js", "type": "file" },
    { "value": "node_modules", "type": "folder" },
    { "value": "docs", "type": "folder" },
    { "value": ".autotmp", "type": "folder" },
    { "value": "__pycache__", "type": "folder" },
    { "value": "vibe_images", "type": "folder" },   // ← 新增
    { "value": "tools", "type": "folder" },          // ← 新增（同步脚本，不属于运行时）
    { "value": ".DS_Store", "type": "file" }         // ← 新增（assets/images/.DS_Store 也在包里）
  ]
}
```

> 更彻底的做法：把 `vibe_images/` 整个移到仓库根目录（项目根，不在 `miniprogram/` 下），从源头断掉入包路径。

### 2. 删掉 app.json 里冗余的全局组件注册

现状：`app.json` 全局注册了 `custom-nav / article-card / article-list / loading / empty-state` 五个，而**每个页面的 `.json` 里又按需注册了一遍**（已核对，全部页面注册完整，无遗漏）。全局注册会导致每个页面（包括 4 个 tabBar 页）都注入全部 5 个组件的 JS + WXML + WXSS。

```jsonc
// app.json —— 整段删除 usingComponents
- "usingComponents": {
-   "custom-nav": "/components/custom-nav/custom-nav",
-   "article-card": "/components/article-card/article-card",
-   "article-list": "/components/article-list/article-list",
-   "loading": "/components/loading/loading",
-   "empty-state": "/components/empty-state/empty-state"
- },
```

已核对的页面级注册清单（删全局后不会漏）：

| 页面 | 已注册 |
|---|---|
| home / classify / favorite / mine / article / about / daily / download / help | `custom-nav`（+ 各自需要的卡片） |
| search | `article-card` `empty-state` `loading` |
| category-detail | `custom-nav` `article-list` |
| components/article-list | 内部已注册 `article-card` `loading` `empty-state` ✅ |
| index | 不用组件 ✅ |

## 三、P1 启动与运行时（改动集中在 3 个文件）

### 3. `steps.js` 按篇拆分 + 惰性 require —— 详情页从解析 1.37 MB 降到 40 KB

**问题**：`pagesA/utils/content.js` 顶层 `require('../data/steps.js')`，只要打开任意分包页面（哪怕只看「帮助」），1.37 MB 的对象字面量就会被完整解析进内存。低端机这段解析约 100~300 ms。

**方案**：拆成 34 个分片文件，用静态 require 映射表惰性加载（小程序构建工具能识别箭头函数内的静态路径）。

```
pagesA/data/steps/
  ├── b01.js   (31.5 KB)
  ├── b02.js   (29.5 KB)
  ├── ...
  ├── b08.js   (40.8 KB)
  └── index.js (映射表，不含正文)
```

```javascript
// pagesA/data/steps/index.js —— 只放映射，文件本身很小
module.exports = {
  b01: () => require('./b01.js'),
  b02: () => require('./b02.js'),
  b03: () => require('./b03.js'),
  // ... 34 篇
};
```

```javascript
// pagesA/utils/content.js
const data = require('../../utils/data.js');
const STEP_LOADERS = require('../data/steps/index.js');

const _cache = {};
/** 单篇正文：只解析这一篇 */
const loadSteps = (id) => {
  if (!_cache[id] && STEP_LOADERS[id]) {
    _cache[id] = STEP_LOADERS[id]() || [];
  }
  return _cache[id] || [];
};

/** 全文检索才需要全量，且只在用户主动搜索时触发 */
const loadAllSteps = () => {
  Object.keys(STEP_LOADERS).forEach(loadSteps);
  return _cache;
};

const getArticleById = (id) => {
  const meta = data.getArticleById(id);
  if (!meta) return null;
  return { ...meta, steps: loadSteps(id) };   // ← 只解析 40 KB
};

const searchFull = (keyword) => {
  const stepMap = loadAllSteps();              // ← 仅搜索时全量
  /* 其余逻辑不变 */
};
```

> ⚠️ 配套动作：`tools/sync-articles.mjs` 目前只写 `pagesA/data/steps.js`，改成按篇写分片（34 个文件）+ 生成 `index.js`。拆分脚本本身是幂等的，可反复跑。

**预期收益**：详情页 JS 解析 1.37 MB → 40 KB；「帮助/关于/下载」等轻页面不再背 1.37 MB；搜索页行为不变（搜索本来就要全量）。

### 4. 系统信息同步 API 缓存（每个页面省 2 次同步调用）

`custom-nav` 的 `attached` 每次都跑 `wx.getSystemInfoSync()` + `wx.getMenuButtonBoundingClientRect()`，8 个页面 × 每次进页都在跑。缓存到 `globalData` 即可：

```javascript
// utils/util.js —— 加缓存
let _sysInfo = null;
const getSystemInfo = () => {
  if (_sysInfo) return _sysInfo;
  try {
    _sysInfo = wx.getSystemInfoSync();
  } catch (e) {
    _sysInfo = { statusBarHeight: 20, screenWidth: 375, screenHeight: 667, safeArea: { bottom: 667 } };
  }
  return _sysInfo;
};

let _navBarHeight = null;
const getNavBarHeight = () => {
  if (_navBarHeight != null) return _navBarHeight;
  const menuButtonInfo = wx.getMenuButtonBoundingClientRect ? wx.getMenuButtonBoundingClientRect() : null;
  const statusBarHeight = getStatusBarHeight();
  _navBarHeight = menuButtonInfo
    ? (menuButtonInfo.top - statusBarHeight) * 2 + (menuButtonInfo.height || 32)
    : 44;
  return _navBarHeight;
};
```

### 5. 去掉两处人为的 300 ms 假延迟

数据全在本地，不需要「假装请求」。`setTimeout(..., 300)` 让列表页和搜索结果平白慢 300 ms。

```javascript
// pagesA/category-detail/category-detail.js —— loadArticles 去掉 setTimeout，直接 setData
- setTimeout(() => {
-   this.setData({ articles: ..., loading: false, hasMore: ... });
-   if (reset) wx.stopPullDownRefresh();
- }, 300);
+ this.setData({ articles: reset ? list : [...this.data.articles, ...list], loading: false, hasMore });
+ if (reset) wx.stopPullDownRefresh();
```

```javascript
// pagesA/search/search.js —— doSearch 同理去掉 300 ms 包裹
```

### 6. 首页实时搜索加防抖（已现成的工具函数没用上）

`utils/util.js` 里 `debounce` / `throttle` 已定义但全项目 0 调用。首页 `onSearchInput` 每敲一个字就全量 `searchAll` + setData 10 张卡片：

```javascript
// pages/home/home.js
const { debounce } = require('../../utils/util.js');

Page({
  onLoad() {
    this._doSearch = debounce((kw) => {
      const { articles } = searchAll(kw);
      const favorites = app.globalData.favorites || [];
      this.setData({
        searching: true,
        searchResults: articles.slice(0, 10).map(a => ({ ...a, isFavorite: favorites.includes(a.id) }))
      });
    }, 200);
  },

  onSearchInput(e) {
    const keyword = e.detail.value;
    this.setData({ searchKeyword: keyword });
    if (!keyword) { this.setData({ searching: false, searchResults: [] }); return; }
    this._doSearch(keyword);   // ← 200 ms 防抖
  },
});
```

## 四、P2 渲染体验（锦上添花，可择机做）

### 7. 详情页分段渲染（44 条 → 先渲染 15 条）

`b01/b02/b05/b08/b13` 这 5 篇都是 41~44 条，首屏一次性建 600 个节点。改成先出 15 条，触底追加：

```javascript
// pagesA/article/article.js
const STEP_CHUNK = 15;

loadArticle(id) {
  const raw = getArticleById(id);
  const all = decorateSteps(raw.steps);
  this._allSteps = all;
  this.setData({
    article: { ...raw, steps: all.slice(0, STEP_CHUNK) },   // ← 首屏只传 15 条
    hasMoreSteps: all.length > STEP_CHUNK,
    /* 其余字段不变 */
  });
},

onReachBottom() {
  const all = this._allSteps || [];
  const cur = (this.data.article && this.data.article.steps.length) || 0;
  if (cur >= all.length) return;
  const next = all.slice(cur, cur + STEP_CHUNK);
  this.setData({
    [`article.steps[${cur}]`]: next,          // ← 按路径追加，不重传已渲染部分
    hasMoreSteps: cur + next.length < all.length
  });
}
```

### 8. setData 瘦身：相关推荐只传卡片用得到的字段

`getRelatedArticles` 返回的是带 `content`（导语数组）的完整索引对象，而 `article-card` 只消费 `id/cover/title/brief/categoryName/categoryColor/isFavorite`。裁剪后再 setData：

### 10. 分包预下载策略微调

现状只在 `pages/home/home` 配了 `network: "all"`，即 4G 下也预下载 1.4 MB。两个选择：

- **体验优先（推荐保持现状）**：`all`，用户点进详情页零等待；
- **流量优先**：改 `"network": "wifi"`，4G 下首次进详情页会有 1~3 秒下载。

如果做了第 3 项（steps 分片），预下载的下载量不变但首屏解析大幅变快，两项叠加效果最好。

另外建议给启动页也加上，覆盖「首次安装直接点搜索」的路径：

```jsonc
"preloadRule": {
  "pages/index/index": { "network": "all", "packages": ["content"] },
  "pages/home/home":  { "network": "all", "packages": ["content"] }
}
```

## 六、落地顺序建议

| 轮次 | 动作 | 收益 | 风险 |
|---|---|---|---|
| 第 1 轮 | P0-1（vibe_images 排除）+ P0-2（删全局组件） | 主包 1.74 → 0.87 MB | 无 |
| 第 2 轮 | P1-4（系统信息缓存）+ P1-5（去假延迟）+ P1-6（搜索防抖） | 进页更快、列表/搜索快 300 ms | 无 |
| 第 3 轮 | P1-3（steps 分片，含同步脚本改造） | 详情页解析 1.37 MB → 40 KB | 中（需改同步脚本，建议先在分支验证） |
| 第 4 轮 | P2 分段渲染 / setData 瘦身 / 图片 | 长文首屏、流量 | 低 |

> 前两轮纯减法、零功能改动，建议优先做；第 3 轮收益最大但要动同步脚本，建议单独分支验证后再合。
